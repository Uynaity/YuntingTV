# E:跨来源全局搜索

父任务:[08-11-radio-db-migration](../08-11-radio-db-migration/prd.md)
前置:[B 云听/蜻蜓装载入库](../08-11-radio-db-s2-crawlers/prd.md)——需要三来源目录齐备

## Goal

一次搜遍三个来源的完整目录。这是整个数据库化方案**最初也是最主要**的动机。

今天做不到:`pickSource` 只选一个来源,`scopedChannels` 按 (来源, 地区, 分类) 取范围,
搜索索引建在那个范围上。所以搜索天然被限制在「用户当前屏幕的筛选条件」内。

## 现状与差距

- **TuneIn 的跨地区搜索今天已经能用**:`Channels(provinceCode=0)` 会合并全部国家
  ([source_tunein.go:365](../../../radio-proxy/source_tunein.go))。[search.go:184](../../../radio-proxy/search.go)
  那句「不做跨地区全站搜」是产品选择,不是机制限制。
- **云听不行**:`(0,0)` 只返回 19 条全国台(实测),完整目录须逐地区枚举 → 只有入库后才拿得到。
- **蜻蜓不行**:每 scope 上限 300(`pagesize=300` 硬编码),且 APP 已隐藏「全部」入口。
- **跨来源不行**:三个来源三份独立索引,没有合并层。

## Requirements

1. 搜索数据源为 DB 的完整目录,不再是 `scopeCache` 的某个范围
2. **拼音索引仍在内存**:`syllablesOf` 的多音字候选、首字母滑窗回溯是 Postgres 做不了的
   (`pg_trgm` 也替代不了「音乐之声 → yyzs」)。形状是「DB 全量快照 → 建一份全局索引 → 内存里搜」
   ——TuneIn 今天就是这个形状,只是数据源是 JSON 文件
3. 索引在装载完成后重建,不跟着 `channelsTTL` 走
4. **结果去重**:同一 `content_id` 因跨地区在库里有多行(TuneIn 125 台),搜索结果须按
   `content_id` 去重并确定展示哪一行的地区
5. **跨来源重复不合并**(本版):「北京音乐广播」在云听和蜻蜓下 `content_id` 完全不同,
   自动合并需要判据(台名归一化?带地区?),那是独立的产品决策。
   **本版按来源分组展示**,把合并留到「来源合并」任务
6. 接口形状待定:新端点还是 `/v1/search` 加参数(如 `source=all`)。
   出参仍为 `Channel` 列表,但需带来源标识供 APP 分组
7. **APP 需要加入口**——这是新功能,「APP 零改动」的约束对本任务不适用

## 非目标

- 不做来源合并/去重(见上)
- 不做节目单搜索、主播搜索
- 不改现有单来源搜索的行为(范围内搜索仍保留)

## 开工前要定的产品问题

- 跨来源结果怎么排?(按来源分组?混排后按匹配度?)
- 同名台在两个来源都命中时,展示两条还是提示「同一电台,两个播放源」?
- 全局搜索是独立入口,还是在现有搜索框上加一个「搜全部」开关?

## Acceptance Criteria

- [ ] 一次查询可覆盖三来源全部约 25000 个台(云听 940 + 蜻蜓 1098 + TuneIn 23215)
- [ ] 拼音搜索行为与今天一致:首字母(bj → 北京广播)、全拼、打一半(beij)、多音字(音乐之声 → yyzs/ylzs)
- [ ] 前缀命中排在非前缀命中之前(与 `matchChannels` 现有排序口径一致)
- [ ] 同一 `content_id` 在结果中只出现一次(跨地区多行已去重)
- [ ] 索引构建耗时与内存占用有实测数字并记录(TuneIn 两万余台几乎全英文,`syllablesOf` 返回 nil,
      真正要算拼音的是云听/蜻蜓的中文台名)
- [ ] 搜索不触发任何上游请求
- [ ] 现有单来源范围内搜索行为不变,回归测试通过
