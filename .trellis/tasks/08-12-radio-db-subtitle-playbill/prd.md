# C:subtitle 改由节目单推算

父任务:[08-11-radio-db-migration](../08-11-radio-db-migration/prd.md)
前置:无技术依赖,但与 [D 列表读取切 DB](../08-11-radio-db-s3-cutover/prd.md) 合用才有意义
——D 需要它才能真正做到「用户请求零上游调用」。

## Goal

把 subtitle(卡片上那行「正在播什么」)的来源,从**电台列表接口**改成**节目单推算**。

这是整个数据库化方案的关键一环。原方案里 subtitle 仍要现场调 `Source.Channels()`,
而那正是身份字段进库想省掉的那次调用——**DB 因此一次上游调用都省不掉**。
改由节目单推算后,这个死结解开。

## 依据(实测)

- 云听 `web/appProgram/listByDate`、蜻蜓 `v3/channels/{id}/playbills` 均返回
  `title` + `startTime` / `endTime`(epoch 毫秒),取覆盖 `now()` 的那档即为当前节目
- 实测蜻蜓某台的推算结果与列表的 `current_program`、单台接口的 `nowplaying` **三者一致**
- 网关 `programsTTL` 已有「找出覆盖当前时刻的那档」的现成逻辑,两个来源可共用

**成本**:云听 940 + 蜻蜓 1098 = **2038 次/天 ≈ 1.4 次/分钟**。
对比今天(活跃范围 × 48 次/天,20 个范围即 960 次)约为两倍,但全部发生在后台调度,
不在用户请求路径上。

## Requirements

1. 后台按日为每个电台拉取当天节目单并缓存;subtitle = 覆盖 `now()` 的那档标题
2. **用户请求路径零上游调用**:subtitle 从本地缓存/DB 计算得出
3. 云听须带签名(实测无签名一律 `code 1001`);沿用服务端现有 `ytSign`
4. **失败降级**:某台节目单拉取失败 → subtitle 留空,不阻断该台的列表展示
5. TuneIn 不参与:它的 `subtitle` 已随目录入库,本就不实时(阶段1 已确立)
6. 顺带把节目单缓存下来供 `/v1/programs` 复用,避免同一份数据拉两次
7. `channelsTTL` 对齐 `:00/:30` 的设计在本任务后可以退休——它的存在理由就是 subtitle

## 已知取舍(必须记录,不要事后当成 bug)

**节目单是按日拉的,当天临时改档不会反映。** 今天列表下发的 subtitle 反映的是上游实时状态,
改为推算后会丢失这部分精度。换来的是:精确到节目边界(而非 30 分钟一档的近似)、
用户请求不阻塞上游、上游挂掉时降级而非报错。

若实测发现某来源临时调整频繁,备选方案:蜻蜓有免签名的单台接口
`v4/channels/{id}`(带 `nowplaying`),可为「用户当前屏幕上这一屏」按需补实时值;
**云听没有按 id 查单台的接口**,只有节目单这一条路。

## 非目标

- 不改 `/v1/programs` 的对外契约
- 不预抓「全部电台 × 每一天」——只拉当天,历史/未来仍按需
- 不动 TuneIn

## Acceptance Criteria

- [ ] 云听、蜻蜓的 subtitle 由节目单推算得出,与改动前的列表 subtitle 抽样 ≥30 个台比对一致
      (差异项须能归因到「节目边界更精确」或「临时改档」,不能是错档)
- [ ] `/v1/channels`、`/v1/search`、`/v1/channels/by-ids` 在请求路径上**不再调用**
      云听/蜻蜓的列表接口
- [ ] 节目单拉取全量一轮耗时与请求数落在预期量级(≈2038 次),且可限速
- [ ] 单台节目单失败时该台 subtitle 为空,列表其余部分正常
- [ ] 节目单缓存被 `/v1/programs` 复用,同一天同一台不重复拉取
- [ ] 跨零点正确切换到新一天的节目单(日界按北京时间,与 `cnZone` / `qtDayWindow` 同口径)
- [ ] `go vet` + 全量测试通过
