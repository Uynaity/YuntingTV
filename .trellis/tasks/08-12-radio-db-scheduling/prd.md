# F:装载调度与陈旧告警

父任务:[08-11-radio-db-migration](../08-11-radio-db-migration/prd.md)
前置:[B 云听/蜻蜓装载入库](../08-11-radio-db-s2-crawlers/prd.md)——要等三个来源的装载命令都存在

## Goal

**让三个来源的目录自动保持新鲜,并且在它悄悄停摆时能被发现。**

今天三个装载命令全靠手敲。父任务契约 8 说的「装载频率各按各的成本」目前只是一句话,
没有任何东西在执行它;契约 6 的陈旧告警也还没有实现。

这两件必须一起做:**定时器和告警是一对**。只加定时器,「数据可控」会在某天变成
「静默过期」——而那正是本项目要消灭的失败模式,不是引入它的地方。

## 为什么 TuneIn 不再需要特殊处理

原先担心 TuneIn 因上游 IP 配额爬不完(整棵树 3000+ 次 Browse,爬虫设计成「403 即停、
换 IP 续爬」)。**用户已实测:带 `TUNEIN_PARTNER_ID` 时可以在单个 IP 下一次爬完。**

→ 不需要增量爬、不需要 IP 池、不需要改爬虫。挂定时器即可。
爬虫现有的断点续爬逻辑**保留不动**,它现在的角色是保险丝而不是常规路径。

## Requirements

1. **三个来源各自的定时装载**,周期按各自成本(实测):

   | | 抓取成本 | 建议周期 |
   |---|---|---|
   | 蜻蜓 | 4 次请求,秒级 | 日级 |
   | 云听 | 320 次请求,约 2.5 分钟 | 日级 |
   | TuneIn | 3000+ 次 Browse,小时级 | 周级 |

   差异**只体现在调度配置里,代码里不留分支**(契约 8)。

2. **TuneIn 的两段仍然分开**:爬虫产出 JSON → `-import-tunein` 转换装载。
   定时任务把两段串起来跑,但**不合并**——合并等于让「改一条清洗规则」去付
   「重爬一遍全球」的钱(阶段1 已否决)。那个 JSON 文件是爬虫的断点 + 转换的输入,
   **不是服务端依赖**(A 已把服务端的文件依赖删干净),不要试图消灭它。

3. **陈旧告警**(契约 6):用各表的 `updated_at` 做健康检查,超阈值告警。
   阈值按各自周期给,不是一刀切。

4. **装载失败必须可见**。B 的语义是「任一子请求失败即整轮放弃、不写库」——
   这在无人值守下的表现是「数据没变,也没人知道」。失败要出现在告警里,
   不能只写进日志。

5. **不引入新的运行时依赖**。调度用部署环境已有的东西(cron / compose 的
   `restart` + sleep 循环 / 宿主机 systemd timer,三选一,择最简);
   告警走已有的出口,不新起监控栈。

6. **调度器不进请求路径**。装载是一次性命令,和网关进程分开跑,
   崩了不影响服务(契约 1:装载是唯一写者,服务端只读)。

## 非目标

- 不改爬虫的抓取逻辑(断点续爬保留,不做增量)
- 不做「立即生效」:装载完成后 ≤30 分钟由 scopeCache 自然过期带出新数据(A 已确立)
- 不做管理后台/可视化,告警能到人即可
- 不动读取路径

## 开工前要定的

- [ ] 告警的出口是什么(邮件 / Telegram / 别的)——决定第 3、4 条怎么落
- [ ] 调度放在哪(宿主机 cron vs compose 里的常驻容器)——决定第 5 条怎么落

## Acceptance Criteria

- [ ] 三个来源各自按周期自动装载,跑通至少一个完整周期
- [ ] TuneIn 的「爬 → 装载」两段自动串起来,单 IP 一次跑完(实测)
- [ ] 装载失败(含 B 的整轮放弃)会触发告警,不是只写日志
- [ ] 陈旧告警按各来源的周期分别设阈值,**并验证过一次真实告警**
      (人为让某个来源超期,确认告警真的到人——契约 6 明确要求这一条)
- [ ] 装载进程崩溃/被杀不影响网关服务
- [ ] 未引入新的运行时依赖
- [ ] 一轮装载失败后,旧数据仍在服务(整份替换的事务语义,B 已保证)

## Notes

- 本任务是「数据可控」这个目标的**最后一块**:B 让数据进得来,F 让它一直是新的、
  并且停了有人知道。少了 F,前面所有工作会在某天悄悄退化成一份过期快照。
