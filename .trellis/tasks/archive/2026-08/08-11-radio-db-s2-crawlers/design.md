## 决策 1:两个来源的抓取形状不统一,也不该统一

| | 请求数 | 一次能拿到什么 |
|---|---|---|
| 蜻蜓 | **4** | 全部字段:id / title / cover / province_id / category_ids |
| 云听 | **320** | 32 次拿全量清单 + 288 次(地区×分类)拿分类归属 |

差一个数量级,原因是上游能力不同:**云听的电台对象里根本没有分类字段**(实测),
分类只能靠「按分类查一遍」反推。这不是实现选择,是上游给什么就只能拿什么。

父任务契约 8 要统一的是**表结构与读取路径**,不是抓取形状。抓取侧硬套一个共同抽象
(什么 `Crawler` 接口、什么分页策略对象)只会造出一个两边都不合身的壳。
两个来源各写各的装载函数,共用的只有:整份替换的事务写入、重试退避、空结果拒绝。

**实现语言:Go**,沿用阶段1 的理由 —— 复用 `source_*.go` 里已有测试覆盖的解析代码,
不在 Python 里重写一份会漂移的副本。`ytSign` 尤其不能重写。

## 决策 2:云听的目录取「并集」,不以 `categoryId=0` 为准

实测数字打架:

```
categoryId=0 逐地区枚举  → 937 台
地区 × 9 个分类 枚举     → 942 台
```

有 **5 台只出现在某个分类下**、**1 台只出现在「全部」里**。两边都不是完整目录。

→ 取并集(**943**)。这不是「兼容上游脏数据」,这正是本任务要买的东西:
今天用户能看到哪些台,取决于上游两个接口谁答得全;入库后由我们决定。

代价:装载要跑满 320 次请求才能算出并集,不能只跑 32 次省事。

## 决策 3:`play_url_low` 两个来源性质不同,不能一视同仁

- **蜻蜓**:`https://ls.qingting.fm/live/{id}/64k.m3u8`,无签名,实测直连 200。
  由 id 完全推得 → 装载时算出来存。存的是**推导结果**,不是运行时配置,不违反契约 2。
- **云听**:签名 URL,`key` 被强制校验(篡改/去掉都是 403),`time` 是签发时刻。
  → **照原样存,但把它当作有时效的值对待**:`updated_at` 就是签发时刻,读取侧
  (D)据此判断新鲜度。

**B 不做「只刷 play_url_low 的快作业」。** 理由:TTL 还没实测出来,现在加就是凭想象
加机制;而且那属于读取路径的新鲜度问题,是 D 的范围。B 的交付物里包含**把 TTL 测出来**,
让 D 有据可依 —— 这比现在拍脑袋加一个 30 分钟的定时器有用。

> 若实测 TTL 短到连一天都撑不过,D 的选项是:①32 次请求的快刷新作业;
> ②`/v1/stream` 对云听改成现场取址(它今天返回空 url,改成真取址是一次 API 行为变更,
> 要连 APP 一起看)。两条都不在 B 里决定。

## 决策 4:整份替换的失败语义比 A 更严

A 的空拒绝只看「转换结果里有没有台」。B 面对的是**几百次网络请求**,
半路失败的表现是「目录少了一个省」——这比空目录更危险,因为它写得进去。

```
任一子请求在重试耗尽后仍失败 → 整轮放弃,一行都不写
```

不做「尽力而为,写多少算多少」。那等于把上游的抖动直接变成用户可见的丢台,
而「数据可控」正是本任务要买的第二样东西。

重试:每个请求最多 4 次,退避 0.5/1/1.5/2s。实测 288 次并发 10 一次没失败,
但上游间歇返空是实测撞到过的,重试不是防御性编程。

写入沿用 A 的 `writeTuneInRows` 形状:单事务、按 `source` 删光再插、四张表一起。
**抽成一个跨来源共用的写入函数**——这三个来源写的是同一组表,这里是真有共性的地方。

## 决策 5:「全部」哨兵行由装载侧写进表

蜻蜓的「全部地区」「全部分类」今天是网关合成的(`source_qingting.go:71,:90`),
上游没有。落库后由**装载侧写进 `radio_provinces` / `radio_categories`**,读取侧原样输出。

理由:D 要把三个来源收敛成一套 SQL 读取。如果哨兵留在读取侧拼,
每个来源就各带一段「补哨兵」的分支,那套统一读取就白统一了。
写进表里,读取侧只有一句 `SELECT ... WHERE source=?`。

> A 里 TuneIn 的分类哨兵目前仍由 `tiCategoriesFrom` 在读取侧拼(表里其实也有那一行)。
> 两边都在,不冲突;D 收敛读取路径时统一挪到表侧。

## 决策 6:容忍缺字段,但只在实测撞到的地方容忍

实测:蜻蜓有 1 台(`province_id=471`「50首经典古典音乐」)**没有 `province` 对象**,
且 `v4/regions` 不含 471 —— 它今天在 APP 里没有任何地区入口能到达。

→ `radio_channels` 照写 `province_code=471`;`radio_provinces` **不为它造行**
(地区清单以 `v4/regions` 为准,不从电台反推)。后果是它只能被 E 的全局搜索找到,
与今天一致,不算退步。

不做泛化的「所有字段都判空」:没实测到的缺字段就让它按零值走,
真出问题时是一条能看懂的错误,比一堆静默兜底好查。

## 决策 7:subtitle 一律留空,即便响应里就有

蜻蜓的 `current_program.title` 就在列表响应里,云听的 `subtitle` 也是。
按契约 7 **不写入** —— 它由 [C](../08-12-radio-db-subtitle-playbill/prd.md) 从节目单推算。

存了会更糟:装载是日级的,一个日级陈旧的「正在播放」比空白更误导。

## 决策 8:不动读取路径,一行都不动

B 的产出只有装载命令和数据。`source_yunting.go` / `source_qingting.go` 的
`Provinces`/`Categories`/`Channels` 在本任务里**保持现状继续服务线上流量**,
它们同时被装载侧当解析器复用。切读取是 D 的事。

→ 本任务合并后线上行为必须**零变化**,这也是它能安全先合的原因。
