# 低性能 Android TV 性能审查与架构重构

## Goal

为低内存、低 CPU/GPU 性能的 Android TV 建立可验证的性能基线，并重构电台浏览、播放和节目单的数据流，使冷启动、快速切台、分页滚动和全屏播放不会因无界并发、宽范围 Compose 重组或高成本图片效果导致卡顿、内存峰值或崩溃。

## Requirements

- 以当前 `gateway-edition` 分支代码为唯一行为基线，保留现有来源、搜索、分页、收藏、回放、睡眠定时、MediaSession 后台播放和 APK 更新能力。
- 所有可取消的请求必须具备结构化并发和 latest-wins 语义：来源/筛选/搜索/分页/节目单/流解析/回放解析不能用过期响应覆盖当前状态，也不能在用户快速操作时累积无界请求。
- 播放器连接失败、网络失败、媒体解析失败和安装器失败必须转化为可恢复状态，不得从主线程回调或协程边界直接导致进程崩溃；取消必须保持 `CancellationException` 语义。
- 首屏必须先完成可交互内容渲染，再按需连接播放器、恢复自动播放和检查更新；启动阶段不能被播放器服务、流类型解析或更新检查串行阻塞。
- 高频播放进度只在播放器面板可见且确有播放内容时运行，并在最窄的 Compose 子树收集；电台 Grid 不得因进度刷新而重组。
- 远程频道分页由单一可取消的分页数据流负责；节目单和“当前节目”刷新必须按频道/日期键控并带 TTL/去重。收藏刷新不得在用户可感知路径中按地区下载全量频道列表；需要网关提供批量按 ID 查询或当前节目批量查询契约。
- 全屏背景和封面图片必须有明确尺寸、单次解码和有界缓存；低性能设备不得使用全屏原图 `RenderEffect` 模糊或在转场期间长期保留两套重型画面。
- 增加针对竞态、取消、播放器连接失败、分页和缓存的自动化测试，并增加低端 TV 的 Macrobenchmark/Perfetto 验证入口。

## Constraints

- 单模块 MVVM + Jetpack Compose for TV、Media3 `MediaSessionService`、Retrofit/OkHttp、Coil、DataStore 继续使用；不为远端目录引入 Room/SQLite。
- `radio-proxy` 不在本仓库中，批量刷新接口需在设计中定义为外部前置条件；客户端在接口未部署时应保留旧数据并降级，不得因接口缺失崩溃。
- 不改变已有 DataStore key 的含义，不泄漏来源 DTO，不在 release 增加高体量日志。
- 生产重构分阶段提交，每阶段都有可回滚边界；不得以增加更多定时器或 catch-all 补丁掩盖竞态。

## Acceptance Criteria

- [x] 冷启动、首次列表展示、自动播放、手动播放、切来源/地区/分类、搜索、分页、打开节目单、回放和全屏播放的请求/状态时序有单一 owner，快速操作只保留最新请求。
- [x] MediaController/PlaybackService 连接失败只展示错误或保持未连接状态；不会出现主线程未捕获 `Future.get()` 异常或永久等待播放入口。
- [x] 500ms 级进度刷新不再订阅根屏；在进度变化时网格可见项不发生重组，且 ticker 在无播放/后台/无订阅时停止。
- [x] 低性能设备全屏播放不创建全屏原图模糊 RenderEffect；背景位图和调色板由一次有界尺寸加载产生，并有 URL 级有界缓存。
- [x] 收藏跨来源展示使用稳定且唯一的复合键，不会因相同 `contentId` 触发 LazyGrid key 崩溃或误路由。
- [~] 单元测试覆盖过期响应、取消传播、连接失败、分页边界、节目单 TTL/去重、播放 latest-wins（66 项，已覆盖）；
      **基准脚本未做** —— 无低端 TV 实体设备，改以 `PerfCounters` 的确定性计数（请求扇出/解码/重组）替代。
- [~] `./gradlew testDebugUnitTest lintDebug assembleRelease` 全过（0 error / 15 既有 warning）。
      已记录：网络请求数量（逐场景 PerfCounters 读数）、GPU/bitmap 内存（GL 231.6→73.6MB、PSS 378→233MB，真机实测）。
      **未记录**：冷启动耗时与帧时长 P50/P95/P99 —— 同上，无基准设备。
